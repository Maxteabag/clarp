# Differences from the Python Host, on purpose

The Rust Host joins the fleet on the contract the apps already speak. Where it differs from the
Python Host in something a client can see, the difference is in this file with its reason, or it
is a bug. The conformance run (`../conformance`) finds the differences; this file explains the
ones that stay.

## Differences that are registered one by one

**Conversation views and Stop queue notices.** The Rust Host's conversation
views (#702, Host contract 145) add `chat_view` to the agent snapshot and
`view` and `session_rows` to conversation rows. The retired Python reference
has no such fields. In `stop-with-queue` it sends a generic `queue-updated`
after the event that starts golf, repeating the paused state, depth 2 and
revision 6. Rust emits the start event with that state once. The ten observed
differences are registered in `conformance/intended.txt` from run 45051582445.

**Self-prompts and reminders in Conversation view.** The Rust Host gives
the agents' audience to a local `clarp-admin prompt` from an agent to itself
and to reminders delivered by its scheduler or local prompt timer. These
prompts and their final replies stay in Session view. A dispatch for the
agents sends the prompt's origin and Session tag on the event stream. A
tell-user note is visible in Conversation, and a user's steer opens the
existing audience split. Python's issue 702 implementation already made the prompt itself
Session-only. It excluded an agent addressing itself from coordination, so
the final reply of that turn could still appear in Conversation.

**How the snapshot and the artifact list may be kept (issue 805, Rust contract 181).** The
Python Host answers `GET /agents/snapshot` and `GET /artifacts` with `Cache-Control: no-store`.
The Rust Host answers them with `private, no-cache` and a weak `ETag`, and answers a held tag
with 304, so a phone's own HTTP cache, where it keeps them, revalidates them instead of fetching
them whole each time (an app may also send the tag itself).
The lead's decision of 25 Nov 2026: the Python Host is retired, and its recorded header no longer
binds these two routes. The next conformance run gives these differences their ids. Every other
route keeps `no-store`.

Each has its id in `../conformance/intended.txt`. The id is a hash of the place and both values:
it covers that exact difference and nothing else.

## Rust-first features

- **Roster events carry what changed, and one row can be read alone (issue 809, Rust contracts
  182 and 183).** The Python Host's `agent-roster` events about one agent say only their kind and
  session, and an app reads the whole snapshot for each. The Rust Host adds `agent_id` and
  `fields` (the changed fields of the agent's snapshot row, made by the code that makes the row)
  to the kinds `helper-state`, `mute-changed`, `chat_view` and a beginning `agent-transit`, and
  `parent` (the maker's counts and state) to `helper-state`, and `head_revision` and
  `conversation_id` to `transcript-updated` (feature `roster_fields`); and it
  answers `GET /agents/{session}` with one row of the snapshot (feature `agent_row`). A phone re-read
  a 940 kB snapshot about 300 times an hour for events that changed one or two fields.

- **A turn whose agent's folder is gone says so (issue 758, Rust contract 173).** The Python
  Host started the tool in the agent's folder and, when that folder had been removed, failed
  with the system's words for the program it could not start. The Rust Host looks first: a
  turn, a goal turn, a turn on the Codex chat lane or a fork of an agent whose folder is not
  there, or is no folder, fails at once as `folder_missing` (`failures::OWN_KINDS`), never tried
  again, with a sentence that names the folder and says to recreate it or make a new agent in
  another folder (nothing changes an agent's folder). Only a folder that is not there, or a path that is no folder, counts: a look that
  fails otherwise (a mount away for a moment, a parent that may not be searched) leaves the
  launch to be tried as before. The shim says the same when the folder goes between that look
  and the launch (`clarp_spool::folder_gone`, one source for both). A Codex goal that would go
  on by itself does not while its agent's folder is gone: it looks again every 5 seconds, and
  goes on once the folder is back. The Host's own questions to a model in its default folder say
  so too when that folder is gone. No try brings a folder back, so the ten tries of a refused
  launch only put the failure off. Not covered: a call's opening to such an agent keeps its own
  rule, and is tried again every second for as long as the call lasts, while the caller hears
  nothing; that is an issue of its own.
- **A turn is over at its tool's own end line (issue 750, Rust contract 172).** The Python Host
  ended a turn when its tool's process exited. Claude Code prints its `result`, and Grok its end
  line, 0.7 to 2.7 seconds before it exits (Claude Code sends what it counted first), and the
  agent was shown at work for that long after its answer. The Rust Host ends the turn at that
  line (Codex exec at `turn.completed`), when its answer is whole and nothing else of the turn
  is owed: Claude's result names the turn's own message (a resumed session can first answer,
  in a result of its own, a task notification its last process left behind), no message read
  into it and not answered, none given to it and not yet read, no
  separate turn its process went on to, no tool call that runs, no work Claude Code left in the
  background (it answers again when that is done, and the turn ends at that answer). The agent's
  state, its live items and the row's `turn` (`ended_at_ms` and `worked_ms` with it) say the
  end from that line. The process goes on until it exits, and the agent's next turn is
  begun at once but launched only then: two processes never work in one conversation. A Stop
  meanwhile ends the process and leaves the turn as it ended. A process that exits badly after
  an answer it said was whole leaves the turn completed and is not tried again (that would answer
  twice); the Host's log says so. Anything the process still says after its end line is kept in
  the conversation as the turn's, after its closing row. A process that runs on 30 seconds after
  its turn is stopped as a Stop stops it, and once that Stop has had its time the next turn is
  launched whether the process is gone or not. Claude Code is asked to stop with SIGINT first, then SIGTERM
  after three seconds: interrupted, it prints a `result` of `error_during_execution` some 40 ms
  later, and the stopped turn ends there (with SIGTERM it printed nothing and went a second
  later). A turn with a message given to it and not yet read still ends at the exit, as before.

  turn. The tool is given one prompt that says the user sent these while it was busy and holds
  each in order, numbered `[1]`, `[2]`, and so on; every backend. A later attempt of the turn
  (a failure that passes, a wait for an account, a restart before the launch) is given the same
  prompt, rebuilt from the agent's log, and no takeover replaces it. A turn that ends before it
  did anything for them (words of an answer or a tool, in any attempt), by a Stop that is not
  the user's own (an agent's, a routine's, a newer message sent now) or a lost process, gives the messages after its first back to the head of
  the queue, in order, where they wait with their rows already written (Maximus's ruling of 23
  Nov 2026: nothing the user wrote ends unanswered because someone else stopped the turn). They
  keep the words they were said with: the queue refuses to reword them. A turn that had begun
  its work, and the user's own Stop, end them with the turn. While a turn runs that cannot take such a message now
  (no steering on the backend, or a steer that was not possible), its queue item and the
  `queue-updated` event it joined with say `read_together: true`. The Python Host starts one
  queued message per turn, so its agent answers the first without the others and each of the
  rest in a turn of its own; it has no `read_together`.

- **Agent activity feature advertisement (feature 156).** The Rust Host
  advertises `agent_state` to clients that gate on it. Both Hosts already
  send `agent-state` and `agent-activity` in the base event stream.

- **Stalled live turns (issue 249, Rust contract 149).** When a running tool
  has produced no stdout or stderr for the configured duration and a fresh user
  or Oracle message is waiting, the Rust Host exposes the stall and the existing

  Both fields are null when a turn is not stalled.

  threshold still determines when the stall is reported. The retired Python

Issue 272. The Rust Host wakes registered iPhones silently when a chat starts or
finishes work or crosses an account or user wait that can change its badge.
The app refreshes the roster and applies the unread rule to its device-local
read state. The Host coalesces these background pushes, with at least a minute
between wakes and at most three wakes per hour. iOS decides whether to deliver
each wake. Reply alerts continue to request a refresh through
`content-available`, and the Host leaves `aps.badge` unset because it cannot
compute the phone's unread count.

Issue 278. The Rust Host accepts a device's calendar result at
`POST /calendar/response` with `request_id`, `session` and `status`
(`added`, `declined` or `failed`). The requesting agent receives the first
result through its normal queue. The response window is 24 hours, up to the
most recent 4,096 requests in the current Host process. The Host publishes
`calendar-response` after admission.

A full app can post `{"text":"..."}` to `POST /teams/{id}/messages` for an
active team with communication enabled. The post is attributed to User in
the feed and is available to current team members in their next team brief.

`GET /task-plan` returns the most recently changed paused plan if the agent
has no active plan. A plan revision publishes `task-plan-updated` with
`session`, `agent_id`, `plan_id` and `revision` after the changed plan is
readable. Native Codex goals continue to use `goal-updated`.

On a Rust Host coordination turn that a user's message joins, a note that answers
the user gives the rest of the turn back to the agents (rule FU, contract 164,
feature `turn_audience_returns`). It is decided by place, so it is the same on the
first read and after the end: reply text written after a note that followed the
user's latest message there is the agents' as a draft, once stored and after the
end; the live turn's `audience` goes back to `agents` at the note, and a later
message of the user's makes it `user` again. The note, the user's messages and
what was written before the note stay visible. The Python Host never gives such a
turn back to the agents.

A call's header (what an agent the user speaks to in a call is told was said since it last
spoke) quotes as the user's only what the user said: a message of origin `user`, or the
Oracle carrying their words. Another agent's message, a goal's wake, a scheduled prompt and
the Host's own prompts are left out (issues 732 and 734). An answer of the agent is quoted,
and counts as the agent having spoken, when it was said in the call: in a turn the user
began, after the user's words joined a turn of another origin (to that turn's end), or as
the opening line of a call it placed; what it answered the others is left out (issue 735).
The Python Host quotes every message and answer but those of its routine automation
(heartbeat, leader tick, dreaming, janitor, system), a message as "User -> <persona>: …",
and counts every such answer as the agent having spoken. Since issue 732 the hands-free
router, too, leaves a goal's wake out of what an agent was last told.

Issue 217 (feature contract 150) gives the Rust Host's original paired VoIP recipients

An agent imported by a move (`POST /agents/import`) is held on the Rust Host
until the move is handed over: every message, the user's included, waits in its
queue, and nothing starts until the hand-off's resume (`POST /turn-queue/resume`,
or the app's Resume). The import's answer says so (`held: true`). The Python Host
has no import (the move is the Rust Host's migration route); until 22 Nov 2026 the
Rust Host held only the agent's own work after an import and ran what its user said.

Issue 216 (feature contract 151) adds per-call mode selection to the Rust Host.
The Python Host requires a Live default for user-started Live calls. The Rust Host

A waiting message of the owner's can be read into the running turn, or take it over, on the Rust

Conversation forks (issue 718, contract 153, feature `conversation_fork`) are available
on the Rust Host only, for the agents its owner names in `[conversation_forks] agents` of the
Host's `config.toml` (read anew at each message and each snapshot; the snapshot says so per
agent as `conversation_fork`). In Conversation view, a message of the user's to such a Claude
Code agent while its own turn works for other agents is answered at once by a fork of the
agent's session (`--resume <session> --fork-session --session-id <fork>`), in the same
conversation; the next message goes to the same fork, and the agent's own next turn opens with
a note of what the fork was asked, said and did. `/live` shows the fork's turn, with the agent's
own as `main_turn`; `POST /stop` stops the fork's turn first (`target: "main"` for the agent's
own). A fork's tools run with `CLARP_FORK=1`: `clarp-agent-bg job-upsert|job-restart`,
`clarp-admin agent create|fork` and `clarp-sub-agent start|fork` refuse it (exit 77), and
a hook of its own refuses Claude Code's file edits (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`). Known limit, accepted
for issue 718: a fork's first action can repeat in the window between that action and the
read of it, when the agent's own turn ends in that window or the Host is away; the message is
then answered once, by the agent's own session.
