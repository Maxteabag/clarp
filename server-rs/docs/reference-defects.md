# Defects of the reference

What the conformance runs showed to be wrong, or unsteady, in the Python Host. The Rust Host does
not copy these. Each is reported to whoever owns the Python Host's releases; none is fixed from
here.

| # | What | Evidence | State |
|---|---|---|---|
| R1 | A message sent again under the same `client_msg_id`, after it was answered, leaves the conversation in one of two shapes: the reply is either the row written while the turn ran (with the turn's end on it), or the row imported from the tool's transcript (another id, no `turn`). Which one depends on timing | Conformance runs 43678950870 and 43679413710, scenario `retry-same-client-id`: the reference differs from itself | Scenario marked `unsteady`: compared, not counted. To report |
| R2 | `docs/protocol.md` section 4 says a plain send to a busy agent preempts the running turn unless `queue_if_busy` is set. For a user's message the Host queues it: `POST /send` answers `queued: true`, the running turn completes, the new message runs after. The code says so itself (`turn_claim._enqueue_if_busy`: "in-flight turn running → queue a user send; legacy other origins preempt") | Run 43679413710, scenario `send-while-busy` | The Rust Host does what the Python Host does for a user. The document is what is wrong. To report |
| R3 | Right after a turn ends, `GET /log` can show the reply twice, or show a state that changes a moment later: the Host is still importing the tool's transcript and folding it into the rows it wrote while the turn ran | Run 43678950870: two runs of the unchanged Host differed in 27 places until the driver waited for the conversation to stop changing | The driver waits three seconds of no change. A client has no such signal: it sees the intermediate states |
| R4 | After a Stop, messages that were already queued stayed held after `POST /turn-queue/resume`, and while held they counted as work in progress and suppressed the agent's goal wakes; `POST /turn-queue/<id>/send` answered 500 and removed the row | Observed on the live Host on 15 Nov 2026 (not by the suite); related issues 320, 249 | Report drafted, waits for the owner's word |
| R5 | A plain send that has to wait changes the queue (`queue_depth` 1, `queue_revision` 1 in its answer) and no `queue-updated` event says so; only the sender knows. A send with `queue_if_busy` is announced | Runs 43679413710 and 43680705704, scenarios `send-while-busy` and `queue-while-busy` | The Rust Host announces every message that joins the queue. Registered as a difference. To report |
| R6 | The reply that closes a turn has `phase: "final"`, except when the turn before it had already settled: then the later reply has `phase: null`. The same reply, read at the same point, in two scenarios | Run 43680705704, scenarios `two-turns` and `log-pages` (the second reply), against `queue-while-busy` and `send-while-busy` (both replies `final`) | The Rust Host says `final` for every reply that closes a completed turn. Registered as a difference. To report |
| R7 | A plain send from something that is not a person ("legacy other origins") ends the running turn of a busy agent | Read in `turn_claim._enqueue_if_busy`; not run by the suite | The Rust Host lets no automation end a running turn: the message waits its turn. To report |
| R8 | When a queued message starts as the turn before it ends, the two rows that change (the reply that closed the turn, the message that starts) get their revisions in either order, from run to run | Run 43683008178, scenario `queue-while-busy`: the two recordings of the unchanged Host differ in exactly this | The Rust Host writes both in one write, always in the same order (the message, then the end of the turn before it). Both recordings are kept; the Rust Host matches one. To report |
| R9 | Defect R1 without a retry: after a single plain turn the reply is sometimes the row imported from the tool's transcript (another id, no `turn` on it, one revision more) instead of the row written while the turn ran | Run 43683008178, scenario `text-turn`: the second recording of the unchanged Host | Both recordings are kept; the Rust Host matches the first. To report with R1 and R3: they are one defect seen three ways |
| R10 | The preview of a notification for a spoken reply shows the bracketed emotion tags the speech engine acts out (`[sigh]`). Everywhere else the same reply is shown without them: the list of chats, the chat itself. The preview is cleaned from the blocks' inner text, where the rule "inside `<speak>`" no longer sees them | Run 43686638701, scenario `voice-markup`: preview `synthetic spoken part. [sigh] done.`, `last_message` without the tag | The Rust Host cleans the preview as what it is, something spoken. Registered as a difference. To report |
