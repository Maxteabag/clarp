# Defects of the reference

What the conformance runs showed to be wrong, or unsteady, in the Python Host. The Rust Host does
not copy these. Each is reported to whoever owns the Python Host's releases; none is fixed from
here.

| # | What | Evidence | State |
|---|---|---|---|
| R1 | A message sent again under the same `client_msg_id`, after it was answered, leaves the conversation in one of two shapes: the reply is either the row written while the turn ran (with the turn's end on it), or the row imported from the tool's transcript (another id, no `turn`). Which one depends on timing | Conformance runs 43678950870 and 43679413710, scenario `retry-same-client-id`: the reference differs from itself | Scenario marked `unsteady`: compared, not counted. To report |
| R2 | `docs/protocol.md` section 4 says a plain send to a busy agent preempts the running turn unless `queue_if_busy` is set. For a user's message the Host queues it: `POST /send` answers `queued: true`, the running turn completes, the new message runs after. The code says so itself (`turn_claim._enqueue_if_busy`: "in-flight turn running → queue a user send; legacy other origins preempt") | Run 43679413710, scenario `send-while-busy` | The Rust Host does what the Python Host does for a user. The document is what is wrong. To report |
| R3 | Right after a turn ends, `GET /log` can show the reply twice, or show a state that changes a moment later: the Host is still importing the tool's transcript and folding it into the rows it wrote while the turn ran | Run 43678950870: two runs of the unchanged Host differed in 27 places until the driver waited for the conversation to stop changing | The driver waits three seconds of no change. A client has no such signal: it sees the intermediate states |
| R4 | After a Stop, messages that were already queued stayed held after `POST /turn-queue/resume`, and while held they counted as work in progress and suppressed the agent's goal wakes; `POST /turn-queue/<id>/send` answered 500 and removed the row | Observed on the live Host on 15 Nov 2026 (not by the suite); related issues 320, 249 | Report drafted, waits for the owner's word |
| R5 | A plain send that has to wait changes the queue (`queue_depth` 1, `queue_revision` 1 in its answer) and no `queue-updated` event says so; only the sender knows. A send with `queue_if_busy` is announced | Runs 43679413710 and 43680705704, scenarios `send-while-busy` and `queue-while-busy` | The Rust Host announces every message that joins the queue. Registered as a difference. To report |
| R6 | The reply that closes a turn has `phase: "final"`, except when the turn before it had already settled: then the later reply has `phase: null`. The same reply, read at the same point, in two scenarios | Run 43680705704, scenarios `two-turns` and `log-pages` (the second reply), against `queue-while-busy` and `send-while-busy` (both replies `final`) | The Rust Host says `final` for every reply that closes a completed turn. Registered as a difference. To report |
| R7 | A plain send from something that is not a person ("legacy other origins") ends the running turn of a busy agent | Read in `turn_claim._enqueue_if_busy`; not run by the suite | The Rust Host lets no automation end a running turn: the message waits its turn. To report |
| R8 | When a queued message starts as the turn before it ends, the two rows that change (the reply that closed the turn, the message that starts) get their revisions in either order, from run to run | Run 43683008178, scenario `queue-while-busy`: the two recordings of the unchanged Host differ in exactly this | The Rust Host writes both in one write, always in the same order (the message, then the end of the turn before it). Both recordings are kept; the Rust Host matches one. To report |
| R9 | Defect R1 without a retry: after a single plain turn the reply is sometimes the row imported from the tool's transcript (another id, no `turn` on it, one revision more) instead of the row written while the turn ran | Run 43683008178, scenario `text-turn`: the second recording of the unchanged Host | Both recordings are kept; the Rust Host matches the first. To report with R1 and R3: they are one defect seen three ways |
| R10 | The preview of a notification for a spoken reply shows the bracketed emotion tags the speech engine acts out (`[sigh]`). Everywhere else the same reply is shown without them: the list of chats, the chat itself. The preview is cleaned from the blocks' inner text, where the rule "inside `<speak>`" no longer sees them | Run 43686638701, scenario `voice-markup`: preview `synthetic spoken part. [sigh] done.`, `last_message` without the tag | The Rust Host cleans the preview as what it is, something spoken. Registered as a difference. To report |
| R11 | `turn_started_at` in `GET /agents/snapshot` is documented as the start of the current turn (`agents.turn_started_at`: "Epoch ms of the current (or most recent) turn start") and is computed as the first busy state after the last `done`, `idle` or `stopped`. A turn that ends as `interrupted` is none of those (a Stop by the user, a usage limit, a runner that exited, a restart of the server), so the turn after it is counted from the start of the interrupted one, or from the first of several in a row | Measured read-only on the live Host on 15 Nov 2026, three days of `state_log`: 356 of 1,873 turn starts (19%) name an earlier turn's start: 184 after a usage limit, 142 after a runner exit, 13 after a user's Stop (in the middle 10 minutes too early, at most 6.5 hours), 11 after a server restart, 6 after a turn that did not start. Conformance run 43699456714, scenario `turn-timer-after-stop`, both recordings: while the turn after a stopped one runs, the field is the stopped turn's start | Fixed in the Python Host on 15 Nov 2026 (PR 357, from the measurement here): `interrupted` ends a turn too. The Rust Host gives the start of the turn that runs, and 0 at rest; the difference is no longer registered |
| R12 | After a turn that had waited in the queue has ended and the conversation has settled, `last_completed_message` in `GET /agents/snapshot` is still the user's message (`You: ...`), while `last_message` and `last_message_id` are the agent's answer. The rule leaves out an answer that is still counted as live (`message_previews._agent_preview`: an assistant row whose source is `live:`), and the answer of such a turn stays so. After a turn that did not wait, the same field shows the answer | Run 43699456714, scenario `turn-timer`, both recordings, against `turn-timer-after-stop` and `text-turn` | The Rust Host shows the answer. Registered as a difference. Unsteady: in run 43715117293 the first of the two recordings showed the answer, and the second the user's message. To report; it belongs with R1, R3 and R9 (what the Host does with the tool's transcript after a turn) |
| R13 | The agent's `model` in `GET /agents/snapshot` stays empty after turns that completed, in one run of two | Run 43703416886, scenario `turn-timer`: the first recording shows no model at any reading, also at rest after two completed turns; the second shows it from the second turn on | Both recordings are kept; the Rust Host shows the model of the last completed turn, which is what the second recording shows. In run 43719479954 both recordings of `approval` show no model after the turn that the delivered answer began; that place is registered as a difference. To report with R1, R3 and R9 |
| R14 | A message the Host sends an agent by itself moves the user's focus to that agent: the answer to a request when it is delivered, a goal that is taken up again, a schedule that is due, a heartbeat. Focus is "which agent the user currently has open" (`lib/focus.py`), and an un-named message goes to the agent that has it. The move comes from one line: every dispatch to a named session counts as "addressed by name" (`turn_admission._dispatch_owned`: `forced_session` gives `routed_by_name=True`, and that sets the focus). The janitor was taken out of it on purpose (`not janitor_run_id`, and `tests/unit/test_janitor_dispatch.py::test_valid_run_is_silent_queued_idempotent_and_does_not_change_focus`); the other automatic senders were not | Conformance run 43713907614, scenario `approval`, both recordings: no message was ever sent to the agent by a person, and after the answer was delivered `GET /agents/snapshot` names the agent as `focus` and its row says `focused: true`. Read in the code for the other senders; not measured on the live Host | The Rust Host moves the focus only when the user does something: selects an agent, or writes to it. Registered as a difference. To report: with several agents working toward goals, the agent a hands-free message goes to changes under the user |
| R15 | The answer to `POST /artifacts/<id>/discard` for a pinned artifact says `pinned: true` beside `pinned_at: null`. The discard unpins the artifact (`artifacts.discard` clears `pinned_at`), and the answer is built from the row as it was read before, with only the three changed times replaced (`{**current, "deleted_at": now, "updated_at": now, "pinned_at": None}`), so the truth value that was derived from the old `pinned_at` stays | Conformance run 43713907614, scenario `library`, both recordings. The vectors of the rules show the same (`tools/artifact-vectors.py`) | The Rust Host says `pinned: false`. Registered as a difference. To report |
| R16 | The reply that closed a turn is written again when the next message arrives, in some runs: its revision moves above the revision of the message that came after it. Seen after turns that something other than a person began (another agent, a schedule, automation, a watcher), not after a person's. A client that catches up by revision is given that reply a second time | Conformance run 43715954622, scenario `who-is-told`, the final `GET /log` in both recordings: after two of the four such turns in both recordings, after the other two in one recording of two | Not a difference a client can rely on either way. The run now compares revisions by the cursors a client holds, which this does not touch. To report with R1, R3 and R9 |
