# Generic identity boundaries

Clarp source, defaults, protocols, fixtures, and documentation must not assume
the identity of a particular user or machine. This boundary separates identity
that must be removed from identifiers that must remain stable for compatibility
or distribution.

## Prohibited in current behavior

- A real user's name, email address, account handle, session slug, or decision
  vocabulary in runtime copy, schema fields, protocol fields, examples, skills,
  fixtures, or documentation.
- A developer's absolute home path, hostname, private or Tailnet IP address, or
  local checkout path.
- A specific GitHub owner, container registry namespace, or repository URL as a
  runtime fallback. Install and update flows must use recorded source metadata
  or explicit configuration.
- A signing identity, Apple team, provisioning-profile name, or App Store
  numeric identifier embedded in reusable project source.

Use role names such as `user`, `agent`, `computer`, and `app owner`; temporary
paths and network addresses in tests must be generated by fixtures.

## Stable distribution identity

Bundle IDs, App Group IDs, keychain access groups, StoreKit product IDs, APNs
topics, and the published App Store record identify an installed application,
not its end user. Changing them in place breaks upgrades, keychain access,
sharing, notifications, subscriptions, and TestFlight continuity.

Therefore:

- the shipped Clarp application may retain its established bundle namespace;
- reusable project and CI inputs should accept an explicit bundle namespace,
  team, profiles, signing identity, and App Store app ID;
- tests may assert the production identity only when testing the production
  target itself, and generic project templates must use placeholders;
- a future rebranded application uses a separate migration and distribution
  plan rather than a blind textual replacement.

## Compatibility-only legacy names

Old XDG directories, service units, environment variables, database columns,
tables, and command names are allowed only inside bounded migration code and
migration regression fixtures. They must never be used as a new default or
shown as current product terminology.

Compatibility code must:

1. discover legacy state without using a developer-specific path;
2. copy or atomically move durable configuration, SQLite state, uploads, media,
   credentials, models, skills, and user-value documents before activation;
3. preserve rollback until the new release passes readiness;
4. handle both old-only and old-plus-new layouts without overwriting either;
5. retire obsolete services and links only after the new service is healthy;
6. keep schema migrations transactional and preserve every existing row.

Removing a legacy spelling from source is not sufficient reason to delete its
migration. Direct upgrades from any supported old release must retain state.

## Product and fixture identities

Clarp's shipped agent personas are product content, not the computer owner's
identity. They may remain when explicitly identified as built-in personas, but
protocol and persistence logic must not treat any persona as the user.

Tests should prefer neutral synthetic identities such as `user`, `agent-a`,
`computer-a`, `example.test`, loopback addresses, and temporary homes. Provider
brand names remain where they describe real integrations.

## Current audit findings

The first exhaustive working-tree scan found remaining identity-sensitive
references in these groups:

- repository and registry ownership in installation, update, Docker, and
  historical documentation;
- production Apple bundle/App Group/product identifiers across native targets,
  APNs defaults, signing workflows, and verification scripts;
- a numeric App Store ID in the legacy Linux upload helper;
- one hard-coded Tailnet address and one machine hostname in networking notes,
  cache tooling, and APNs fixtures;
- a concrete session slug in the web session-selection fixtures;
- production account handles in sanitizer fixtures;
- generated signing-cache files containing the production bundle ID;
- historical PR links whose owner is archival provenance rather than runtime
  configuration.

The final scan should classify every remaining hit as removed, parameterized,
synthetic, archival provenance, stable distribution identity, or bounded legacy
migration. Unclassified hits fail the productization review.
